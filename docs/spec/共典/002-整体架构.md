# 002 · 整体架构：S3 混合分层（声明式解释器结算权威 + S2 属性级逃生门）

> **来源**：[GitHub #3 解法评论](https://github.com/YunxiLuna/TRPGTogether/issues/3)（方式：prototype，走查 2 场景 + 七维打分 + 拍板）。
>
> **为什么（人类可读）**：本票回答"数值结算层到底谁来管"。选了 **S3 混合分层**——数值结算权威恒为**声明式解释器**（S1 核心），S2（LLM 生成可执行代码+沙箱）只作**属性级逃生门**而非主结算层。核心理由：S2 是黑盒，不可逐条回算、副作用不可追溯，与"事实分临时/正典两级"冲突；而 S1 声明式解释器逐条可回算、账本副作用可追溯，代价是表达力有限（复杂迭代/递归表达不了）——这代价用 S2 逃生门兜底。下游 003–008 全部假设统一为"声明式 schema + 解释器结算 + 账本层仲裁"。

## 决议（正式记录）

**选定：S3 混合分层——数值结算权威恒为声明式解释器（S1 核心），S2 生成代码沙箱仅作为"属性级逃生门"。**

### 两个必答题的走查结论

- **引擎与叙事 LLM 分歧谁说了算**：引擎（解释器）输出不可被叙事层覆盖。叙事 LLM 只能"提议数值"，结算永远由解释器按 schema 执行；S2 逃生门即使启用，代码也只是"另一条结算路径"，产物仍写进同一账本，叙事 LLM 无权改写引擎输出。
- **两人同时声称矛盾之事**：仲裁发生在**账本层**而非引擎层（两个值可能都在 schema 内）。按已知结论先提交者正典化，后提交者写旁支账本（`canon:false` + 原因码），缺席/相关方收到角色内视角的传闻注入。

## 放弃项（明确记录）

1. 放弃 S2 作为主结算层：生成代码是黑盒，无法逐条回算验证，账本副作用不可追溯，世界书矛盾场景下旁支标注会失效——与"事实分临时/正典两级"冲突。
2. 放弃"多模型交叉生成"作为标准路径（成本高、冷启动慢）；仅当世界书可量化密度高时作为可选增强（由 007 自动校准票决定是否开启，见 [007 § Q4](./007-自动校准与漂移纠偏.md#q4-自适应严格度密度复用-003-识别信号--3-档曲线零-token)）。
3. 放弃"叙事 LLM 直接写数值"：硬约束"引擎输出不可被叙事层覆盖"不允许。
