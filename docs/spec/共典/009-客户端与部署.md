# 009 · 客户端形态、部署与自我批判

> **来源**：[GitHub #10 解法评论](https://github.com/YunxiLuna/TRPGTogether/issues/10)（方式：grilling 1 轮，Q1–Q4 全按推荐拍板；Q5/Q6 为写进解法的内容直接给出）。
>
> **为什么（人类可读）**：本票攻坚简报「客户端与部署」节 + E（自我批判）+ F（风险与未知）节，是整张图里离"能跑起来"最近的一票。核心设计=**本地服务器（Node 单进程）+ 纯浏览器（零壳零安装）**：006 已定客户端纯渲染零逻辑，桌面原生能力（文件系统/自启/通知）MVP 无消费方；单服务器进程是 token 约束下统一省着花的唯一合理拓扑。部署=单房间 + 一次性房间码/长期 token + 账本文件为事实源 + append-only 无真回滚。模型调用=服务器侧唯一 LLM 网关（缓存单点共享省 2–6 倍 / 限流+本地模型替换 1 处配置 / 隐私）。异步时间线=事件流按 seq 单列 + 筛选器 + canon:false 旁支斜体标记（不做 git 分支图并排）。自我批判 5 条逐条答 + 3 风险卡片（R1 6 基元表达力不足 / R2 KnownSet 增量刷 bug 泄露半径外事 / R3 token 预算超预估）。

## Q1 客户端形态：本地服务器 + 纯浏览器（MVP 零壳）

- 决议 = **本地服务器（Node 单进程）+ 纯浏览器**。玩家开浏览器连 `127.0.0.1:xxxx`（本机）或虚拟 LAN（Tailscale 等）里的服务器地址即可，无安装、无壳、跨平台零成本。
- 理由：006 已定客户端=纯渲染零逻辑（panel_view 服务端裁剪下发），桌面原生能力（文件系统直读、本地 LLM 直连、开机自启、原生通知）在 MVP 阶段**没有消费方**——浏览器通过局域网连服务器，服务器单进程统一管账本+物化视图+LLM 网关，浏览器客户端无状态、可多开、可手机浏览器兜底（简报硬约束 2–6 人局域网，不要求移动端原生）。token 约束下，单服务器进程是统一省着花的唯一合理拓扑（缓存/限流/切片全在一处）。
- GM/玩家分界面：**分界面，同一 Web 应用 2 条路由**（`/player/:role` 与 `/gm`），不分应用。复用 006 Q5 已定"GM=独立世界仪表盘"结论，本票只定它是同应用的另一条路由而非另一个可执行程序（理由同上：原生壳无增益，2 条路由成本≈0）。
- 刻意不做（各带触发条件）：
  - Tauri 桌面壳（打包 .exe/开机自启/原生通知）——触发条件=需要开机自启/原生通知/服务器离线时本地壳直连本地模型 3 项中任一项真实出现；
  - Electron 壳——触发条件同上，且 Tauri 优先（体积/性能更优，JS 生态兼容）；
  - 移动端原生 App——触发条件=真实用户反馈"手机浏览器体验不可用"时补（MVP 手机浏览器可读面板/事件流，够用）。
- 放弃项：纯桌面应用无服务器（每人 1 份账本本地副本，与"多人共享事实"核心矛盾——append-only 单一事实源必须有 1 个写者，004 已定单一结算写者=服务端引擎，桌面纯本地版没有这个写者）、PWA 离线优先（简报局域网部署，服务器与客户端同网络段，"离线"无意义）。

## Q2 房间模型 + 鉴权 + 存档回滚

- 决议 = **单房间**（1 部署实例 = 1 个世界观）+ **一次性房间码 / 长期 token** + **append-only 无真回滚（回退=追加反向 status_transition）**。
- 房间模型：1 部署实例管 1 个世界。2–6 人×1 世界是简报硬约束，多房间=账本+可重建索引+KnownSet/panel_state 物化视图成本 ×N，且简报目标是"多人共享 1 个世界观"而非"1 台机器开 N 个互不相干的世界"，多房间无消费方。刻意不做多房间，触发条件=真实用户要求"1 台机器开 2 个互不相干的世界"时补（届时=同代码库起 2 个进程/端口即可，无需架构改动）。
- 鉴权：**房间码 + 长期 token**。创建房间时服务端生成 1 个一次性房间码（6 位即可，2–6 人局域网场景下碰撞无所谓，且房间码本身只在首次加入时消费）；首次加入时服务端下发长期 token（随机 32 字节，存浏览器 localStorage）；后续请求带 token 即可。放弃纯房间码每次输（每次开浏览器/清缓存都要重新输码，摩擦大）与账号体系（简报无注册需求，2–6 人知道彼此身份，房间码+token 足够；账号体系=引入密码管理/找回，违反"不做公网 SaaS"硬约束的精神延伸——局域网内熟人局不需要）。
- 存档与回滚：
  - 事实源 = **账本文件**（append-only，002 已定"文件为事实源"）；索引 DB（SQLite 或同类）= **可重建索引**，崩了/删了重放账本即恢复（006 Q4 兜底同构：物化视图崩了重放账本可重建）。
  - **无真回滚**：账本 append-only 不可删不可改（硬约束"append-only 事件账本"），"回滚"=追加反向 status_transition 事件（004 已定回退机制）或人工触发 drift_correction（007 Q3 四动作之②），全程可审计、原条目永存。放弃"删最后 N 条账本"式回滚（破坏 append-only，且旁支条目/canon:false 条目删了就无法追溯"当时为什么这么判"，004 已定旁支是设计资产非垃圾）。
  - 存档即账本文件本身（人类可读 YAML/JSONL，可直接 git 版本管理），DB 与物化视图均为可丢弃缓存。

## Q3 模型调用：服务器侧唯一 LLM 网关

- 决议 = **服务器侧**。叙事 LLM、缺席简报（若补文案模板）、007 Q3 四动作之④"世界在修正自身"叙事注入，全部走服务器 1 个 LLM 网关接口。
- 理由（token 约束下三重收益）：
  1. **缓存单点**：世界书切片（003 三级锚定位的原文段）、KnownSet 裁剪后的事件、schema 版本快照，全在服务器内存/本地文件缓存，多人共享；客户端直连=每人 1 份缓存，浪费 2–6 倍 token；
  2. **限流与本地模型替换**：服务器 1 处统一限速/排队，玩家并发 2–6 人叙事请求不会打爆 API 配额；本地模型（如 llama.cpp 起服务）替换 API 只需改服务器 1 处配置，客户端零感知；
  3. **隐私**：玩家行动提议/面板数据/世界书原文全在局域网内，若走 API 也集中在服务器 1 个出口（可审计），客户端直连=每人 1 份 API key 泄露面×玩家数，且 key 存 localStorage 可被 XSS 读走。
- 放弃项：客户端直连 API（隐私/缓存/限流三重劣，与 006 客户端零逻辑矛盾）；混合（服务器主+客户端可选本地模型）——MVP 不需要，复杂度翻倍收益为 0（服务器已可替换本地模型）。

## Q4 异步时间线 / 账本可视化

- 决议 = **事件流（按 seq 排序单列）+ 筛选器**，GM 仪表盘在事件流之上加 KnownSet 矩阵 + suspect 标签列表。
- 玩家界面（`/player/:role`）：
  - 主列 = 账本事件流，按 seq 升序，每行 1 条账本事件（kind/action/fact_ref/value/canon_status），**canon:false 旁支条目=斜体 + 原因码角标**（如 `worldbook_conflict`），与正典条目同列不同视觉（004 已定旁支=账本条目带 canon:false 而非独立账本分支，故**不做 git 分支图式多列并排**——那会误导用户以为旁支是平行世界线，实际是被归档的冲突记录）；
  - status_transition（005 事实分级追加、007 drift_correction 回退）画**回退箭头**（从当前值指向锚点值，seq 时间线上一段小折线）；
  - suspect（007 Q1）/ drift_alert（007 Q2）事件高亮色条（suspect=橙、drift_alert=红）；
  - 筛选器：按角色（我的/全服/某角色）、事件类型（action/fact/status_transition/calibration_check/drift_alert/narrative_correction/rumor_injection）、canon_status（canon/provisional/rejected）三组筛选，纯客户端 filter（数据全量在面板里，006 已定），零额外请求。
- GM 仪表盘（`/gm`）：玩家事件流 + **KnownSet 矩阵**（006 Q5 已定，角色×事实格子，空=该角色不知道，用于信息不对称"漏看"自查）+ **suspect 标签列表**（007 Q1 当前带 suspect 的结算值清单）+ **drift_alert 历史**（007 Q2 触发记录）+ 筛选器同玩家侧。
- 数据源：时间线读**物化投影**（与 006 panel_state 同构的 `timeline_state`，账本 seq 推进增量刷，O(1) 读 as_of_seq），不逐条重放账本（006 Q4 兜底逻辑同构：崩了重放可重建，正常运行读物化视图）。
- 放弃项：多世界线并排（语义不符，004 已定旁支非平行世界线）、纯时间轴无筛选（丢旁支/suspect 高亮，GM 自查无入口）、客户端重放账本（性能劣，006 Q4 已弃）。

## Q5 自我批判（简报 E 节）逐条回答

**① 方案里哪些地方事实上仍依赖人力？**
- MVP 验收场景（修仙大千，008 定死）的 schema 样例与回算算例需要**人工核对 1 次**——确认引擎回算结果与世界书原文一致。这是 1 次性验收动作，非持续人工，且是 003 Q4 验证流水线的"回算"段天然需要（回算=用引擎重算世界书已知样例，样例本身从世界书抄出来=人工抄 1 次）。不违反硬约束"禁止人工逐条录入/审核"——硬约束禁的是"人工替系统建结构/调参"，这里是"人工验收 1 次系统输出"，性质不同（验收=QA 动作，建结构/调参=生产动作）。
- GM 世界仪表盘的**"代入检查"入口**（006 Q5 定死）是信息不对称"漏看"的**唯一人工发现入口**——自动监控（007 三重判定/斜率）只能发现数值漂移，**无法发现"某角色 KnownSet 里本该有 1 条 B 的私有事实但物化视图刷漏了"**（这是叙事层/物化视图 bug，不是数值异常）。这是设计选择非缺陷：物化视图刷漏的兜底=账本重放可重建（006 Q4），人工抽查=在重建之前发现问题的提前量；彻底自动发现"刷漏"需要 1 套独立于物化视图的事实推导器做交叉验证，成本=另造 1 个引擎，违反 token/复杂度克制。
- **诚实标注**：以上 2 处是"人力"残留，但都不是"人工建结构/调参"（硬约束禁的那类），而是"人工验收 1 次"+"GM 工具辅助人工抽查"。

**② 自动生成的 schema 在什么情况下会变成新的预建牢笼？**
- 触发条件 = 某属性真实结算逻辑**确实用 6 基元表达不了**（复杂迭代/递归/外部查表），但系统仍强行用 6 基元"近似"表达——此时 schema 不再是"事实的轻量映射"而是"对事实的扭曲简化"，等价于人工预建结构（只是 LLM 建的而非人建的，性质相同：结构先于事实存在、且错了不易察觉）。
- 缓解措施（004 Q6 已定 3 条件）：S2 逃生门属性级默认关，开启需同时满足①该属性结算逻辑确实用 6 基元表达不了（**非偷懒判定，GM 可在仪表盘看"该属性 6 基元近似值 vs 原始叙事描述"差异**，差异大=该开 S2）②007 Q4 判可量化密度高档（低密度世界书开 S2=为少量属性引入黑盒结算层，不划算）③沙箱产物写同一账本（可追溯、旁支标注不失效）。**双门槛升级判定（003 Q5b）**是另一道闸：新属性要升级为 schema 需同时满足"被公式消费"+"剧情承重量连续 N 轮"，防止"LLM 看剧情里提到某属性 1 次就建 schema"的膨胀。
- 仍可能漏的洞：**6 基元近似值"看起来够用"（误差在 007 Q1 容差带内）但语义已被简化**——此时 suspect 不触发、回退不发生，错误静默累积。缓解=GM 仪表盘"schema 演化历史"（006 Q5 定）可回看每次升级/近似的三级锚依据，人工抽查触发条件=该属性 drift_alert 累计 ≥3 次（007 Q2）时 GM 被提醒"该属性的 schema 可能不准"。

**③ 产生系统性错误而无人察觉，如何被发现？**
- 场景 = 007 Q1 纯规则三重判定的阈值本身算错（如 schema quantity cap 区间在世界书锚点回算时就算错、但回算"通过"了——因为回算用的是同一个错 cap，自洽但不对），后续所有结算都基于错 cap 跑，无 suspect 触发（值总在错 cap 内）、无 drift_alert（斜率稳定）、叙事"看起来合理"（002 已知结论：LLM 优化叙事连贯，错数值被叙事包装后读起来顺畅）。
- 发现路径（3 层，从早到晚）：
  1. **003 Q4 验证流水线"回算"段**：用引擎重算世界书**已知样例**（008 MVP 验收场景自带），若样例输出与世界书原文给出的结果不符=cap/公式错。这是**冷启动期**唯一能抓到"系统性错"的关口（世界书已知样例=ground truth，非 LLM 生成物）。MVP 验收必做这一步（008 验收标准①"schema 生成并通过自洽+回算"）。
  2. **运行期=GM 手动深挖按钮**（007 Q2 降级产物）：当 1 个属性 drift_alert 累计 ≥3 次（007 Q2 阈值之上的累积计数，非单次触发）时，GM 仪表盘弹提示"该属性建议深挖"，GM 点按钮→系统喂该属性全部叙事历史+世界书三级锚原文段给 LLM 做 1 次深度比对（**这是全系统除 007 Q3④叙事注入外第 2 个 LLM 调用点，触发条件严格=drift_alert ≥3 次累积，非每轮跑**，token 克制）。
  3. **兜底=账本 append-only 全量重放**（006 Q4 可重建性质）：任何时候怀疑系统性错，重放账本到当前 seq 用最新 schema 版本重算一遍物化视图，与当前物化视图 diff=漂移量（007 Q2 滑动窗口的全量版）。
- 缓解措施汇总：回算段（冷启动）+ 手动深挖（运行期触发条件严格）+ 账本重放 diff（兜底）。**诚实标注**：第 1 层"回算"依赖世界书自带已知样例——**纯文学世界书（几乎无数值）没有已知样例，回算段空转**，系统性错只能靠第 2/3 层抓，而第 2 层要 drift_alert 累积才触发=反应滞后。这是本方案的真实弱点，非"看起来合理"能掩盖的。

**④ 纯文学世界书（几乎无数值）时 schema 生成退化成什么？**
- 退化形态 = **schema 生成结果≈空**（003 反例"气运"已定死：有数值壳但无消费公式的属性保持自然语言档位 narrative_role 或 高/中/低 枚举，不建 quantity，完整 YAML 见 [schema-示例.md 示例 3](./schema-示例.md#示例-3--气运反例保持自然语言档位不建-int-列)）。6 基元里只有 `mapping`（枚举档位映射）和 `progress`（收集计数，若世界书明确写了"收集 N 件"）可能生成，`quantity`/`formula`/`state_machine` 基本不生成。
- 引擎此时退化为**纯事实账本**（append-only 记录事件，无数值结算、无 suspect 判定、无 drift_alert——007 Q4 低密度档阈值放宽到近 no-op，这是设计选择非缺陷，007 已明确"纯文学世界书本就不该硬卡数值"）。
- 面板此时退化为**传闻层为主**（public 层几乎没有字段，private 层=角色私有秘密 if any，rumor 层=世界书叙事事件的高模糊描述）。**诚实标注**：这是"产品价值稀释"而非"系统错误"——纯文学世界书本来就不是"数值结算"目标场景，系统不该硬造数值。008 MVP 验收素材=修仙大千（高密度），气运反例不进 MVP 主验收脚本（008 Q8 定死），此退化形态在 MVP 不验收。

**⑤ 引擎生成错但叙事一直"看起来合理"，如何被发现？**
- 已在③答过 3 层发现路径。补充 1 条产品层缓解：007 Q3 四动作之④"**世界在修正自身**"叙事注入（LLM 喂漂移指标+世界书切片，写 narrative_correction）=当 drift_alert 触发且 GM 选择执行纠偏时，玩家会看到 1 段"世界主动修正"的叙事（如"灵气潮汐逆转，剑意值回落"），**玩家视角感知到的是"世界活了"而非"系统出错了"**——这是产品卖点（007 已定"丢世界修正叙事卖点=纠不回"），同时是发现通道（玩家若 10 次里看到 8 次"世界在修正"，会自然反馈"这个数值老跳"，人工反馈通道兜底自动化漏网）。

## Q6 风险与未知（简报 F 节）前 3 风险卡片

**风险 1：6 基元表达力不足 → S2 逃生门被迫开启 → 黑盒结算层混入 → 与"账归代码"核心矛盾**
- 描述：若真实世界书（非验收素材修仙大千）存在大量"复杂迭代/递归/外部查表"属性，004 Q6 S2 逃生门 3 条件会被频繁满足，LLM 生成代码沙箱产物进账本=黑盒结算层混入（002 已放弃 S2 主结算层正是因为"黑盒不可逐条回算、副作用不可追溯"），系统退化为"一半账归代码一半账归黑盒"，与核心方向矛盾。
- 早期验证方法：MVP 验收用修仙大千（008 定）跑通后，**加测 1 份"属性复杂"世界书**（如 003 信号调研里"斗罗装逼值公式链"类型——多层嵌套公式+条件分支），统计 S2 逃生门 3 条件的触发率：若 ≥30% 的属性走 S2=表达力真不够，需扩基元（破坏"固定 6 基元=防膨胀第一道闸"）或接受 S2 常态化（破坏 002 放弃项）；若 <10%=6 基元够用，风险解除。验证时点=MVP 验收后立即做（1 份世界书，1 次导入，看触发率）。
- 缓解（已定）：S2 属性级默认关（004 Q6 三条件）；双门槛升级判定（003 Q5b）防膨胀；GM 仪表盘 schema 演化历史可回看每次升级依据（006 Q5）。
